# 评论私信流程等待优化记录

日期：2026-08-24
状态：基线已完成，待进行第 1 轮最小调优

## 修复前记录

- 错误现象：评论私信的安全闭环在界面实际已变化后，仍会等待较长的固定延时才开始下一次页面确认；用户明确反馈启动搜索、进入主页、打开视频/评论、评论用户主页、首屏滚动和切换下一视频均偏慢。
- 稳定复现步骤：在 OnePlus NE2210（`b33aa309`，Android 16）上，以“室内设计师”、搜索指定用户、2 个视频、每视频 2 人、非干跑空白消息安全探测从抖音首页运行至完成。
- 当前预期：页面一旦通过既有节点、OCR 和几何规则确认，就应立即进入下一步；未确认时继续有界观察，不因缩短等待而扩大点击范围或跳过安全门。
- 实际差异：基线日志显示多个动作后先消耗保守固定延时，再启动相同的后置确认。例如：启动后固定等待 5 秒；首视频/评论面板探测分别以 450/550 ms、350/500 ms 起步；下一视频在关闭评论区后固定保留 1,600 ms；翻页轮询间隔为 600 ms。

## 基线时序（同一 2×2 安全探测）

| 场景 | 基线证据 | 观察结论 |
| --- | --- | --- |
| 打开抖音到搜索入口 | `initial_screen_settle_completed` 后才开始初始观察，配置为 5,000 ms | 固定启动等待是首要空耗时 |
| 用户结果到主页 | 结果卡手势后约 2 秒获得 `USER_PROFILE` 新鲜事件 | 已有事件优先确认；不需要增加等待 |
| 主页到首视频 | 首视频点击后第 2 次后置探测才确认视频面 | 固定 450/550 ms 探测节奏可更早采样 |
| 视频到评论面板 | 评论按钮后第 3 次面板探测确认 | 每次均保留状态确认，但前两次间隔偏保守 |
| 评论头像到主页 | 头像点击使用新鲜事件/有界轮询 | 无额外盲等，仅缩短轮询节奏 |
| 首屏到下一页 | 现有配置每次后滚动读取间隔 600 ms | 应更早读取同一确认中的评论面板 |
| 当前视频到下一视频 | 关闭评论区、等待并上滑后才开始探测；其中下一视频结算窗为 1,600 ms | 固定结算窗是主要可缩短部分 |

## 单一根因假设

同一组历史保守固定等待被置于页面确认之前；而七个场景均已具备有界节点/OCR/几何后置确认。仅缩短这些“首次采样和重试间隔”，不改变确认条件、次数上限、手势、OCR预算或风险处理，可以让已经就绪的页面更早被识别，同时尚未稳定的页面仍会留在既有观察循环中。

## 第 1 轮最小修改与验证方案

- 修改范围：仅调整 `TuningConstants` 中与上述七段评论流程直接对应的毫秒级等待；不改状态机、选择器、OCR、几何、点击坐标、手势时长、候选筛选和消息逻辑。
- 风险：低延时样本可能读到过渡树；预期行为是继续下一轮观察或走既有有界失败，不应执行额外点击。
- 验证：先运行完整单测、静态检查和构建；再在同一 NE2210 上执行 2×2 闭环检查启动、用户主页、首视频、评论面板、评论头像和下一视频；随后以单视频、每视频 5 人安全探测覆盖首屏后滚动。全程只允许空格探测，禁止真实消息。
- 设备防锁：无人值守期间每不超过 30 分钟在安全空白位置执行一次模拟点击；每次记录时间。

## 第 1 轮结果：变差

- 相同设备、相同 2×2 配置重测。安装后先刷新了无障碍服务绑定；此前服务未接收任务事件，不计入本轮结果。
- 以 1,500 ms 启动结算窗开始观察后，冷启动的首个窗口仍没有无障碍树。日志连续记录 `initial_context_missing_back` 4 次，随后以“无障碍服务未提供页面树”安全失败。
- 结果：变差。任务未进入搜索，未进入用户主页、评论区或私信，也未发送任何内容。

## 第 2 轮根因假设与最小修改

- 单一根因假设：初始 `UNKNOWN` 已有延后恢复保护，但“根节点不存在”的启动帧会绕过该保护，直接进入旧的盲目 BACK 恢复；缩短首次观察后恰好暴露了这条不一致路径。
- 最小修改：仅在 `WAITING_FOR_HOME` 且初始分类尚未完成时，把“根节点不存在”与 `UNKNOWN` 一样记录并留在既有有界初始观察循环中；不改 BACK 恢复本身，超时后既有安全暂停仍有效。
- 验证：重新运行同一 NE2210 2×2 配置。通过标准为没有 `initial_context_missing_back`，并进入既有搜索/主页/评论状态确认；否则停止本轮继续修改并记录。

## 第 2 轮结果：改善

- 修复后冷启动连续出现 10 个无树帧和后续 UNKNOWN 帧时，日志只记录 `initial_context_missing_deferred` / `initial_unknown_deferred`，没有 `initial_context_missing_back`。
- 同一 2×2 安全探测随后正常进入搜索、用户主页、首视频、评论面板与第二视频；4 位用户均为 `BLANK_PROBE_VERIFIED`，最终 `comment_runtime_terminal outcome=COMPLETED` 并回到记录页。
- 单视频、每视频 5 人安全探测：首屏冻结 4 位候选并顺序完成；自动滚动 1 次后，第一次后滚动读取为空，下一次读取识别 3 位新增候选，处理第 5 位后完成。任务总计 5 次 `BLANK_PROBE_VERIFIED`，未发送真实消息。

## 实施的等待缩减

| 场景 | 原等待 | 调整后 | 保留的安全确认 |
| --- | ---: | ---: | --- |
| 打开抖音后首次观察 | 5,000 ms | 1,500 ms | 初始 HOME/搜索双帧确认；无树/UNKNOWN 只观察，不后退 |
| 评论用户主页状态轮询 | 350 ms | 250 ms | 用户主页、风险页、登录页仍逐帧确认 |
| 用户主页打开首视频 | 450/550 ms | 200/300 ms | 仍需验证视频表面和评论入口 |
| 打开评论面板 | 350/500 ms | 180/300 ms | 仍需确认评论面板；受限重试规则不变 |
| 评论头像刷新重试 | 400/450 ms | 300/250 ms | 仅同一已验证头像允许重试 |
| 首屏完成后的滚动 | 600 ms | 300 ms | 仍检查评论面板、底部标记和新增候选 |
| 切换下一视频 | 1,600 ms + 180/500 ms | 700 ms + 100/300 ms | 仍需新视频指纹、评论入口及有界 OCR 验证 |

## 实测结论与限制

- 缩短的是本项目在页面确认前的固定空等；实际耗时还包含抖音冷启动、页面网络/渲染、无障碍树读取和必要 OCR。冷启动中目标应用约 10 秒才首次提供可用树，这一外部加载时间不会因减少应用内延时而消失。
- 该外部等待期间，修复后不再执行盲目 BACK，也不会因提前采样而点击任何控件。页面一旦具备既有证据，低延时轮询立即继续；首屏翻页实测由 300 ms 的有界读取接管并成功发现新增候选。
- 本轮未调整任何手势时长、几何阈值、坐标、OCR 预算、页面确认次数或消息发送策略。所有新增/调整逻辑均不涉及 Android 几何 px；既有比例几何保持不变。
