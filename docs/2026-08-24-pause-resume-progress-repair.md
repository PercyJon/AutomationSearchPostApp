# 暂停恢复进度修复记录（第 1 轮）

## 当前错误现象

在 B 端用户私信任务中，悬浮窗于首个已选用户尚未完成空消息安全探测时点击“暂停”，任务记录把该用户计为“已处理 1、失败 1”。恢复后，检查点把该用户视为已处理，导致它不会再次进入安全探测。

## 稳定复现步骤

1. 创建 B 端用户私信任务：搜索词“红木沙发”，上限 10，空消息安全探测模式。
2. 启动任务，等待抖音“用户”结果页和悬浮窗出现。
3. 在首个候选用户已被选中、尚未到达私信页前，展开悬浮窗并点击“暂停”。
4. 点击“恢复”，等待任务回到结果页。

## 当前预期行为

暂停只是运行状态，不应把未完成候选计入已处理或失败；恢复后应从持久检查点继续，仍保留完整的可处理额度。暂停、恢复、停止均不得发送真实私信。

## 实际行为差异

暂停后任务显示“处理 1 / 10、失败 1”；恢复后的检查点已含该候选身份，因此该用户被跳过。该行为会使任务在用户上限内少处理一个未完成候选。

## 第 1 轮根因假设

`pause()` 在保存检查点前已将当前候选加入已处理身份集合，并把其审计记录结束为 `PAUSED`；计数函数把 `PAUSED` 视作已处理且失败。恢复时重建检查点，会跳过该未完成候选。

## 最小修改与验证方案

仅在暂停当前用户时将该用户从持久“已处理”集合移除；保留暂停审计记录，但不将 `PAUSED` / `STOPPED` 计入已处理或失败。用同一 B 端复现步骤验证暂停后仍为“处理 0 / 10”，恢复后任务从初始安全流程继续；随后执行评论区私信同样的悬浮窗回归。

## 第 1 轮结果：未修改（安全策略保留）

- **真机 OnePlus NE2210 / b33aa309 / Android 16**：B 端任务的暂停、恢复和停止按钮均有效，恢复会重新检查初始页面，停止会返回 App；全程未发送真实消息。
- 现有 B 端身份在打开目标主页前即写入检查点，暂停后将它记为中断/失败并在恢复时跳过。这会牺牲一个未完成名额，但避免在“已点击私信或已触发空消息探测、结果尚未确认”的边界上重复操作同一账户。
- 本轮不移除该保护：当前实现无法仅凭暂停时机可靠地区分“尚未产生外部动作”与“外部结果等待中”。强行删除身份会引入重复私信或重复安全探测风险。该计数呈现问题保留为后续独立需求，需先定义可持久化的外部动作检查点。
